# Topside 设计文档

> 状态：Draft v0.5 · 2026-11-16（已按 M0 和 M1 的结果更新）
> 项目名：Topside（2026-11-15 定）。
> v0.3 的变化：产品方向从“会话状态栏”改为“任务指挥台”，全文重写。v0.2 的方案与 CodeIsland 高度重合，已放弃。

## 1. 一句话定义

一个常驻 macOS 屏幕顶部的灵动岛，用来**发起、跟踪、验收** coding agent 的任务：按一下快捷键，用一句话把活派给 Claude Code 或 Codex；任务在隔离的工作区里后台运行，岛上显示它走到了哪一步；做完后岛给出结果（改了什么、测试过没过），你在岛上决定复查、合入还是丢弃。

## 2. 背景

### 2.1 要解决的问题

用 agent 写代码时，一个任务的完整过程是：想到一件事 → 找个终端 → 切到对的目录 → 启动 agent → 输入需求 → 等 → 回来看它说做完了 → 自己去看改了什么 → 跑测试 → 决定要不要。这里面真正需要人的只有三个时刻：**说清楚要什么、回答 agent 的问题、判断结果行不行**。其余都是杂务，而且同时跑几个任务时，杂务成倍增加：

1. **派活成本高。** 每开一个任务都要开终端、切目录、处理“两个 agent 别改到同一份代码”的问题。
2. **进度不可见。** 任务在哪个终端、跑到哪一步、是不是在等我，都要切窗口才知道。
3. **验收靠自己拼。** agent 说“做完了”不等于做对了。看 diff、跑测试、找另一个 agent 复查，每一步都要手动做。

### 2.2 现有项目

已有的工具分成两类。下面的内容来自各项目的 README、官网和第三方对比文章（2026-11-15 读取），我没有实际安装试用，所以“没有提到”不等于“一定没有”。

**第一类：刘海上的会话状态栏。**

| 项目 | 规模与许可 | 自述的主要功能 |
|------|-----------|----------------|
| [CodeIsland](https://github.com/wxtsky/CodeIsland) | 约 2.6k star，MIT，Swift | 30 多种 agent；实时状态和最新回复；任务清单进度条；允许、拒绝、始终允许；回答问题；跳转到终端标签；用量；SSH 远程；iPhone 和手表伴侣；推送通知 |
| [Vibe Island](https://vibeisland.app/) | 付费，19.99 美元 | 30 种 agent；批准；回答问题；计划审阅；跳转到十多种终端；用量额度 |
| [Notchi](https://github.com/sk-ruban/notchi) | 约 1k star，GPL-3.0 | 每个会话一个像素角色；情绪分析；费用统计 |

它们的共同点：显示的单位是**终端会话**；是**被动**的，agent 得先在终端里启动，岛才看得到；完成时显示 agent 的最后一条回复，不显示工作结果；会话之间互相独立。

**第二类：并行 agent 工作台。**

| 项目 | 状态 | 自述的主要功能 |
|------|------|----------------|
| Conductor | macOS 应用，免费版加付费版 | 在隔离的 git worktree 里并行运行 Claude Code、Codex 等；应用内 diff 审阅；PR 流程 |
| Crystal | 开源，有来源称已停止维护或改名 | 同类的桌面应用，应用内 diff 审阅 |
| Vibe Kanban | 开源，背后的公司已于 2026 年 4 月关闭 | 多 agent 的看板 |

它们的共同点：是**完整的窗口应用**，你要切到它里面去工作，它是你的第二个 IDE。

### 2.3 本项目的定位

**把第二类的能力（派活、隔离、验收）放进第一类的形态（常驻、不抢焦点、有事才出现）。**

| | 会话状态栏 | 并行工作台 | 本项目 |
|---|---|---|---|
| 单位 | 终端会话 | 工作区 | 任务 |
| 怎么开始一件事 | 自己去终端启动 | 切到应用里新建 | 任意位置按快捷键，一句话 |
| 平时在哪 | 刘海 | 一个独立窗口 | 刘海 |
| 做完之后 | 显示最后一条回复 | 应用内看 diff | 岛上的结果卡片，带验证结果和下一步动作 |
| 多个 agent 的关系 | 各自独立 | 各自独立 | 可以接力：一个实现，另一个复查 |

需要诚实说明的一点：**任务引擎本身（worktree 加并行 agent）不是新东西，Conductor 已经做了。** 本项目的新意在三处：

1. **形态**：不需要打开一个应用。派活像用 Spotlight，跟踪靠余光，验收在岛上完成。
2. **验收是一等公民**：任务的终点不是“agent 停了”，而是“结果被你接受或丢弃”。岛自己跑验证命令，不依赖 agent 的自述。
3. **跨 agent 接力**：让 Codex 复查 Claude 的改动，再把复查意见一键交回 Claude 修。这是配方（见 5.2）的自然产物。

## 3. 目标与非目标

### 目标（v1）

- 从任意应用里，在 5 秒内派出一个任务：快捷键、输入需求、回车。
- 每个任务默认运行在独立的 git worktree 里，多个任务互不干扰，也不碰你正在用的工作目录。
- 岛上实时显示每个任务的阶段。需要你的时候（权限、提问、确认计划、待验收）主动提示。
- 任务完成时给出结果卡片：改了哪些文件、增删行数、验证命令是否通过、agent 的总结。
- 在岛上完成验收：看 diff、追加指令、让另一个 agent 复查、开 PR、合入、丢弃。
- 支持 Claude Code 和 Codex，运行器是明确的扩展点。
- 关掉或重启应用不会丢任务：正在跑的任务继续跑，重启后重新接上。
- 以开源项目的标准来做。

### 非目标（v1 不做）

- **不监测你在终端里手动启动的会话。** 这正是 CodeIsland 做的事，两者可以同时使用。v1.1 考虑“收编外部会话”（见第 12 节）。
- 不做内置的代码编辑器和完整的代码审阅工具。内置的 diff 窗口只读，深入修改交给你的编辑器。
- 不做自定义配方的图形化编辑器。v1 只有内置配方。
- 不做容器或虚拟机级别的隔离。worktree 隔离的是 git 状态，不是机器（见 10.2）。
- 不支持远程机器、iOS、Windows、Linux。
- 不上架 Mac App Store。

## 5. 核心概念

### 5.1 任务

任务是本产品的单位。一个任务包含：

- **需求**：你输入的那句话。
- **仓库**和**工作区**：在哪份代码上做，是否隔离。
- **配方**：按什么步骤做。
- **运行记录**：每一步的 agent 会话、事件流、输出。
- **结果**：最终的改动和验证结论。
- **结局**：被接受（合入、开了 PR、保留分支）或被丢弃。

任务的终点是你做出了处置，而不是 agent 停下来。

### 5.2 配方和步骤

配方是一个任务要走的步骤序列。步骤有三种：

| 步骤类型 | 做什么 | 例子 |
|----------|--------|------|
| `agent` | 让某个 agent 带着一段提示词运行 | 实现、制定计划、复查 |
| `shell` | 运行一条命令，用退出码判断成败 | `npm test`、`swift build` |
| `gate` | 停下来等你确认 | 确认计划后再动手 |

v1 的内置配方：

| 配方 | 步骤 | 适合 |
|------|------|------|
| **快速** | 实现 | 小改动、问答式的任务 |
| **实现并验证**（配置了验证命令的仓库默认用它） | 实现 → 验证；验证失败则把输出交回 agent 修，最多重试 2 次 | 大多数任务 |
| **先计划** | 计划（只读）→ 你确认 → 实现 → 验证 | 较大的、方向不确定的任务 |
| **实现并复查** | 实现 → 验证 → 另一个 agent 复查 | 想要第二意见的任务 |

岛上显示的阶段（计划 ✓ 实现 ◐ 验证 ○）就是配方里的步骤。因为步骤是岛自己编排的，所以进度是真实的，不是从 agent 的输出里猜出来的。

配方在代码里是纯数据（`Codable`）。v1 只有内置的这几个，v1.1 支持从文件加载自定义配方。

### 5.3 工作区

每个任务有一个工作区，有两种模式：

- **隔离（默认）**：为任务新建一个 git worktree 和一个分支。任务之间、任务和你自己的工作目录之间互不影响。
- **原地**：直接在仓库目录里运行。用于不是 git 仓库的目录，或者你明确想让 agent 改当前工作目录的情况。同一个目录同时只允许一个原地任务，后来的排队。

## 6. 用户体验

### 6.1 派活

全局快捷键（默认 `⌥Space`，可改）在岛的位置展开一个输入框，不切换应用。

```
┌────────────────────────────────────────────────────────┐
│ 给 api-server 加上限流中间件，每个 IP 每分钟 60 次▏    │
│                                                        │
│ @api-server    Claude    /实现并验证    隔离           │
└────────────────────────────────────────────────────────┘
  ↩ 派出   ⌘↩ 派出并继续输入   ⇥ 切换选项   Esc 取消
```

- 第一行是需求，`⇧↩` 换行。
- 第二行是四个选项，都有默认值，不改也能直接回车：
  - **仓库**：默认是上次用的。输入 `@` 模糊搜索用过的仓库，或者把文件夹拖进来。
  - **agent**：默认是上次用的。
  - **配方**：输入 `/` 选择。默认按仓库是否配置了验证命令决定。
  - **工作区**：隔离或原地。
- `⌘↩` 派出后输入框不收起，可以连续派多个任务。

命令行里有等价的入口，方便在终端里用，也方便脚本调用：

```bash
topside run "给 api-server 加上限流中间件" --repo . --agent codex --recipe verify
```

### 6.2 岛的三种形态

```
① 收起（常态）                ② 提示（事件触发）
┌─────────────────────┐      ┌────────────────────────────────────────────┐
│ ◐ 2     ▓▓▓  ● 1 ✓ 1│      │ ✓ 修复登录 bug   3 个文件 +42 −7  测试通过 │
└─────────────────────┘      │                       [看 diff]  [稍后]    │
  左：运行中的任务数          └────────────────────────────────────────────┘
  右：等你处理 / 待验收

③ 展开（悬停或点击）
┌──────────────────────────────────────────────────────────┐
│ ● 重构配置加载        Claude   想执行 rm -rf build/    ⋯ │
│                                         [拒绝]  [允许]   │
│ ◐ 加限流中间件        Claude   计划 ✓ 实现 ◐ 验证 ○    ⋯ │
│                                Edit src/middleware.ts    │
│ ✓ 修复登录 bug        Codex    3 个文件 +42 −7 测试通过 ⋯ │
│                       [看 diff] [让 Claude 复查] [开 PR] │
│ ○ 更新依赖            Codex    正在准备工作区          ⋯ │
├──────────────────────────────────────────────────────────┤
│ ＋ 新任务 ⌥Space      历史      ⚙               2 个运行中 │
└──────────────────────────────────────────────────────────┘
```

同时运行的任务数没有上限，所以列表要能容纳很多任务：超过一屏时可以滚动，等你处理的任务始终排在最上面；任务超过 8 个时按仓库分组并可折叠。

- **收起**：有刘海的屏幕上，内容分布在刘海两侧；没有刘海的屏幕上，在菜单栏正中画一个同样大小的黑色胶囊。
- **提示**：只在 6.4 列出的时刻触发，默认 6 秒后收回，鼠标停在上面时不收回。
- **展开**：从岛的位置向下展开。鼠标移出或点击外部后收起。

### 6.3 任务状态

列表按紧急度排序。颜色之外始终配有形状不同的图标。

| 紧急度 | 状态 | 含义 | 图标 |
|--------|------|------|------|
| 1 | `needsYou` | 在等你：批准权限、回答问题、确认计划 | ● 橙，脉冲 |
| 2 | `failed` | 某一步失败且无法自动恢复 | ✕ 红 |
| 3 | `ready` | 所有步骤完成，等你验收 | ✓ 绿 |
| 4 | `running` | 正在执行某一步 | ◐ 白，旋转 |
| 5 | `queued` | 正在准备工作区，或在等同一目录里的另一个原地任务结束 | ○ 灰 |
| — | `closed` | 已被接受或丢弃，进入历史 | 不在列表里 |

### 6.4 需要你的时刻

只有这些情况会弹出提示和播放声音，其余变化只更新收起态的数字：

| 时刻 | 提示内容 | 你能做的 |
|------|----------|----------|
| agent 请求权限 | 完整的命令或文件路径 | 允许、拒绝、接管到终端 |
| agent 提出问题后停下 | 问题原文 | 在岛上输入回复 |
| 到达 `gate` 步骤 | 计划的摘要 | 确认、修改意见、取消任务 |
| 任务进入 `ready` | 结果摘要 | 看 diff、稍后 |
| 任务进入 `failed` | 失败的步骤和原因 | 重试、追加指令、接管、丢弃 |

设置里有“勿扰”开关。开启后不弹提示不出声，只保留收起态的数字。

### 6.5 结果卡片与验收

任务完成后，展开态里这个任务显示为结果卡片：

```
✓ 修复登录 bug                                    Codex · 4 分 12 秒
  3 个文件  +42 −7
  验证  npm test  通过（128 个测试）
  “修复了 session 过期时没有清除 cookie 的问题，并补了两个测试。”

  [看 diff]  [追加指令]  [让 Claude 复查]  [开 PR]  [⋯]
```

卡片上的每一项都来自岛自己的观察，不来自 agent 的自述：改动统计来自 `git diff`，验证结果来自验证命令的退出码。只有引号里的那句总结是 agent 说的，界面上用引号把它和事实区分开。

| 动作 | 做什么 |
|------|--------|
| 看 diff | 打开一个只读的 diff 窗口。窗口里可以“在编辑器中打开工作区” |
| 追加指令 | 输入一句话，在同一个 agent 会话里继续。任务回到 `running` |
| 让另一个 agent 复查 | 用另一个 agent 以只读方式审阅这份改动，复查意见附在卡片上。之后可以“把意见交给原 agent 处理”，这等于自动追加一条指令 |
| 开 PR | 提交未提交的改动，推送分支，创建 PR。执行前显示远端、分支名、标题让你确认 |
| 合入本地分支 | 把任务分支合入它的基线分支。只在主工作目录干净且正处于基线分支时可用，否则说明原因 |
| 保留分支 | 删除 worktree，保留分支，任务关闭 |
| 接管到终端 | 在工作区里打开终端并恢复这个 agent 会话，之后由你手动操作 |
| 丢弃 | 删除 worktree 和分支。需要确认 |

### 6.6 下拉菜单

每个任务右侧的 `⋯` 菜单，按任务状态启用或禁用：

- 查看活动（最近的工具调用和输出）
- 追加指令
- 接管到终端
- 暂停 / 继续
- 重试当前步骤
- 在 Finder / 编辑器中打开工作区
- 复制分支名、复制工作区路径
- 丢弃任务

面板底部是全局菜单：新任务、历史、全部暂停、勿扰、设置、退出。

### 6.7 键盘

- `⌥Space`：派活输入框。`⌃⌥Space`：展开或收起任务列表。两者都可以改。
- 列表内：`↑↓` 选择，`↩` 执行这个任务当前最主要的动作（`needsYou` 时是允许，`ready` 时是看 diff），`⌘Y` 允许，`⌘N` 拒绝，`⌘R` 追加指令，`⌘.` 暂停，`Esc` 收起。
- 岛的窗口平时不接受键盘焦点。只有通过快捷键唤起时才临时成为 key window，收起后把焦点还给原来的应用。

```
 └────┬─────┘   └──────┬───────┘   └──────┬──────┘   └────────▲─────────┘
      ▼                ▼                  ▼                   │ Unix socket
     git         agent 进程（脱离应用独立运行）               │
                 stdout ──► 运行目录下的 events.jsonl    topside-hook（桥接 CLI）
                                    ▲                         ▲
                                    └── 应用持续读取          └── agent 的 hook 调用
```

### 7.2 模块

| 模块 | 职责 | 依赖 |
|------|------|------|
| `TopsideCore` | 任务、配方、步骤、事件的数据模型；任务状态机。纯 Swift，不依赖 AppKit，不出现任何 agent 的名字 | 无 |
| `TopsideEngine` | `TaskEngine`、`WorkspaceManager`、`Verifier`、持久化 | `TopsideCore` |
| `TopsideRunners` | 每种 agent 一个运行器 | `TopsideCore` |
| `TopsideIPC` | 权限请求用的 socket 协议 | `TopsideCore` |
| `topside-hook` | 权限桥接 CLI，由 agent 的 hook 调用 | `TopsideIPC` |
| `topside` | 命令行入口：`run`、`list`、`logs`、`stop` | `TopsideEngine` |
| `TopsideApp` | 窗口、界面、设置 | 以上全部 |

引擎不依赖界面，所以可以只用命令行驱动。这让引擎能够先于界面开发和测试。

### 7.3 数据模型

```swift
struct TopsideTask: Identifiable, Codable {
    let id: UUID
    var title: String              // 由需求的前几十个字生成，可改
    var prompt: String
    var repo: URL
    var workspace: Workspace       // .isolated(worktree:branch:baseCommit:) / .inPlace
    var recipe: Recipe
    var steps: [StepState]         // 每个步骤的状态、运行记录、起止时间
    var status: TaskStatus         // 6.3 的状态
    var attention: Attention?      // 正在等你的事：权限请求 / 问题 / gate
    var result: TaskResult?        // 改动统计、验证结论、agent 总结、复查意见
    var outcome: Outcome?          // .pullRequest(url) / .merged / .branchKept / .discarded
    var createdAt: Date
}

struct Recipe: Codable { var name: String; var steps: [Step] }

enum Step: Codable {
    case agent(role: AgentRole, agent: AgentChoice, access: AccessLevel, promptTemplate: String)
    case shell(command: CommandSource, onFailure: FailurePolicy)   // 命令可来自仓库配置
    case gate(kind: GateKind)
}

enum AgentChoice: Codable { case primary, other, specific(AgentKind) }
// .other 表示“任务所选 agent 之外的那一个”，用于复查步骤
```

### 7.4 任务状态机

```
                  工作区就绪
   queued ──────────────────────► running ◄─────────────────────────┐
     ▲                              │  │                            │
     │ 准备工作区                    │  │ 权限请求 / 提问 / gate      │ 你做出回应
     │                              │  └──────────► needsYou ───────┘
   （新任务）                        │
                                    │ 一个步骤完成
                                    ├──► 还有下一步 ──► running（下一步）
                                    │
                                    │ 所有步骤完成
                                    ├──────────────► ready ──你验收──► closed
                                    │                  │
                                    │                  └─ 追加指令 ──► running
                                    │ 步骤失败且重试用尽，或 agent 进程异常退出
                                    └──────────────► failed ──重试 / 追加指令──► running
                                                       └──────丢弃──────► closed
```

状态机是纯函数 `reduce(task, event) -> (task, [effect])`，副作用（启动进程、跑命令）由引擎执行。这样可以用录制的事件序列做回放测试。

### 7.5 持久化

每个任务一个目录，放在 `~/Library/Application Support/Topside/tasks/<id>/` 下：

```
task.json                 任务的完整状态，每次变化后原子写入
runs/<n>/events.jsonl     这一步 agent 的原始事件流（agent 的 stdout 直接写到这里）
runs/<n>/stderr.log
runs/<n>/meta.json        pid、进程启动时间、命令行、agent 会话 id
```

用文件而不用数据库，是因为这样不需要第三方依赖，出问题时可以直接打开看，也是下一节“重启后恢复”的基础。

**写入频率。** 状态变化（开始、完成、失败等）立即写入。只由 agent 事件引起的小更新（当前活动、最新消息、事件文件的读取位置）合并为每 3 秒最多写一次。M1 的性能采样显示，逐事件的原子写是引擎 CPU 开销的主要来源。这样做不影响崩溃恢复：任务状态和读取位置总是一起写入，崩溃后从上次保存的位置重新读事件，应用到上次保存的状态上，结果相同。

## 8. 关键机制

### 8.1 运行 agent

岛自己启动 agent 进程，用它们的无终端模式。

| | Claude Code | Codex |
|---|---|---|
| 启动 | `claude -p <提示词> --output-format stream-json --session-id <uuid>` | `codex exec --json -C <工作区> <提示词>` |
| 追加指令 | 加 `--resume <会话 id>` | `codex exec resume <会话 id> <提示词>` |
| 只读运行 | `--permission-mode` 的计划模式 | `-s read-only` |
| 复查 | 只读运行加复查提示词 | `codex exec review --base <基线分支>` |
| 注入每次运行的配置 | `--settings <文件>` | `-c key=value` |
| 费用上限 | `--max-budget-usd`（软上限，见下） | 没有对应参数 |
| 费用和用量 | `result` 里的 `total_cost_usd` | 只有 token 数，`review` 时为 0 |
| 接管到终端 | 在工作区里执行 `claude --resume <会话 id>` | `codex resume <会话 id>` |

以上参数和行为在 M0 实测过（详见 `docs/m0-findings.md`）。实测中发现、实现时必须处理的几点：

- **一步是否完成，看进程是否退出。** Claude Code 的子 agent 在后台运行时，一次运行会输出两个 `result`：第一个在子 agent 完成之前。
- **中断由 Topside 自己记录。** M0 中被 SIGINT 中断的 Claude Code 运行，事件流里有一个成功的 `result`，退出码是 0，从输出看和正常完成一样。信号是 Topside 发的，它记下这一点即可。
- **Claude Code 的费用上限是软上限。** 它在两次模型调用之间检查，会超出一次调用的量。界面上称为“费用上限（约）”。
- **Codex 的 `--json` 不包含所有工具调用。** 通过 `exec` 脚本工具执行的命令只出现在 Codex 的会话文件里。v1 只读 `--json`，界面上不假装知道它没报告的活动。

每种 agent 实现一个运行器：

```swift
protocol AgentRunner {
    static var kind: AgentKind { get }
    func detect() -> AgentInstallation?                       // 是否安装、版本
    func launchCommand(for step: AgentStepRequest) -> ProcessSpec   // 命令行、环境、工作目录
    func parse(line: Data) -> [RunEvent]                      // 原始事件流的一行 → 归一化事件
    func takeoverCommand(for run: RunRecord) -> String        // 用于“接管到终端”
    var capabilities: Set<Capability> { get }
}
```

归一化事件 `RunEvent` 包括：会话开始、工具调用开始和结束、文本输出、权限被拒、运行结束（成功或失败、总结、用量）。两种 agent 的原始格式不同，各自维护解析，对未知字段和未知事件类型宽容。

**进程脱离应用运行。** agent 进程在自己的会话里启动，标准输出直接重定向到 `events.jsonl`，不经过管道。应用通过持续读取这个文件来获得事件。这样做的结果：

- 应用退出、崩溃、升级，agent 进程都不受影响。
- 应用重启后，根据 `meta.json` 里的 pid 和进程启动时间确认进程身份（防止 pid 被复用），然后从文件上次读到的位置继续读。
- 事件流天然有完整记录，可以用来排查问题和做回放测试。

**启动方式（M1 实现）。** 引擎用 `posix_spawn` 启动一个很短命的 bash 启动器：新会话、信号恢复默认、不继承任何文件描述符。启动器打开 job control（`set -m`），把一个小外壳脚本放到后台运行，记下它的 pid 后立即退出。于是 agent 从一开始就由系统（launchd）接管，不是引擎的子孙进程，按进程树杀进程的工具（IDE 的任务面板、进程管理器）不会把 agent 连带杀掉。M1 的第一版让引擎直接当 agent 的父进程，就在这一点上出过问题。必须打开 job control：否则 bash 会让后台任务忽略 SIGINT，并把标准输入换成 `/dev/null`。外壳脚本把 agent 的退出码写进 `exit-code` 文件，所以由哪个引擎实例看到 agent 结束都能拿到退出码。提示词写进 `stdin.txt` 作为 agent 的标准输入，不出现在命令行参数里。

没有采用两个 CLI 自带的 `--worktree` 和 Claude Code 的 `--bg`，是为了让两种 agent 的行为由岛统一控制。M0 验证了自己管理进程可行（脱离、重新接上、中断、子进程清理），不需要 `--bg`。

### 8.2 工作区管理

**创建。** `git worktree add <路径> -b topside/<任务短名> <基线提交>`。路径默认在 `~/.topside/worktrees/<仓库名>/<任务短名>`，可在设置里改。基线默认是派活时仓库当前分支的 HEAD。

**选择 git。** Topside 不直接用 PATH 里的 `git`：用户机器上可能有很旧的版本（M0 的测试机上 PATH 里是 2018 年的 2.16，不支持 `git worktree remove`）。启动时依次检查 `/usr/bin/git`、`/opt/homebrew/bin/git`、PATH 里的 git，选第一个不低于 2.25 的，并显示所用的路径和版本（`topside doctor`）。agent 在 worktree 里自己调用旧版 git 不受影响，M0 验证过。

**准备。** 新的 worktree 里没有未被 git 跟踪的文件（`.env`、`node_modules`、构建缓存等），很多项目因此跑不起来，或者第一次构建很慢。每个仓库可以在设置里配置以下几项，都是可选的：

| 配置 | 作用 | 例子 |
|------|------|------|
| 要复制的文件 | 从主工作目录复制到 worktree | `.env`、`.env.local` |
| 要克隆的目录 | 用 APFS 写时复制（`cp -c`）把目录瞬间克隆到 worktree，几乎不占额外空间。只适用于不含绝对路径的目录 | `node_modules` |
| 准备命令 | 在 worktree 创建后运行一次 | `npm ci` |
| 验证命令 | `shell` 验证步骤使用 | `npm test` |

“要克隆的目录”不能通用：M0 里克隆 SwiftPM 的 `.build` 后构建失败，因为它的缓存里写死了绝对路径。设置界面上对常见目录给出提示。

第一次对某个仓库派活时，岛会提示这些可以配置，也可以跳过。

**改动统计。** 在 worktree 里用一个临时索引计算（`GIT_INDEX_FILE` 指向临时文件，`read-tree HEAD` 后 `add -A`，再 `diff --cached --numstat <基线>`）。这样能同时统计已提交、未提交和未跟踪的文件，并且遵守 `.gitignore`，又不会动 worktree 真正的索引。

**并发。** 对同一个仓库的 `git worktree add` 和 `remove` 按提交顺序排队执行。M1 的 50 任务测试发现，同时运行时一个 git 进程会读到另一个还没建完的 `.git/worktrees/<名字>`，报错 `failed to read .../commondir`。每次操作只需几十毫秒，排队几乎没有代价；复制文件、准备命令和 agent 本身仍然并行。

**清理。** 岛不会自动删除任何 worktree 或分支。只有“丢弃”“保留分支”“合入”这些你明确点击的动作会删除 worktree。设置里有一个列表显示所有由岛创建的 worktree 和它们占用的空间，可以手动清理已关闭任务留下的。

**岛只在自己创建的 worktree 和 `topside/` 前缀的分支上做写操作。** 唯一的例外是“合入本地分支”，它有 6.5 里写的前置检查。

### 8.3 配方执行

引擎按顺序执行步骤：

- `agent` 步骤：用运行器启动进程，读事件流，进程成功结束则步骤完成。同一个任务里角色相同的后续 agent 步骤默认复用同一个会话（用 `--resume`），这样“验证失败后交回去修”时 agent 还记得之前做了什么。
- `shell` 步骤：在工作区里执行命令，保留输出的最后 200 行。退出码非 0 时按 `onFailure` 处理：把输出作为新的指令交回上一个 agent 步骤重试，或者直接让任务失败。
- `gate` 步骤：任务进入 `needsYou`，等你确认。

提示词模板里可以引用前面步骤的产出，例如复查步骤的模板会带上任务的原始需求和改动范围。模板是内置配方的一部分，放在仓库的资源文件里，方便社区改进。

### 8.4 权限

岛启动的 agent 没有终端，所以权限请求不能回落到终端提示，必须由岛来处理。这是整个设计里安全上最敏感的部分。

**每个 `agent` 步骤有一个访问级别：**

| 级别 | 能做什么 | 用在哪 |
|------|----------|--------|
| 只读 | 读文件、搜索。不能改文件，不能执行有副作用的命令 | 计划步骤、复查步骤 |
| 工作区内（默认） | 可以改工作区里的文件。执行命令时，预先允许的安全命令直接放行，其余的要问你 | 实现步骤 |

v1 **不提供**“跳过所有权限确认”的级别（Q5）。理由：worktree 隔离的是 git 状态，agent 执行的命令仍然作用在你的机器上，无人值守时风险更高。Codex 自带的操作系统级沙箱是另一层保护，默认开启。

**权限请求的路径：**

```
agent 想执行需要批准的操作
   └─► agent 的 hook 调用 topside-hook
          └─► Unix socket ──► PermissionBroker ──► 任务进入 needsYou，岛上提示
                                                        │ 你点击
          ◄──────────────── 决定 ◄──────────────────────┘
   ◄── topside-hook 按 agent 规定的格式把决定写到 stdout
```

hook 的配置通过每次运行的 `--settings`（Claude Code）或 `-c`（Codex）注入，**不修改你的全局配置文件**。这比 v0.2 的方案干净：不需要安装器去合并 `~/.claude/settings.json`，卸载应用后不留任何痕迹。

**安全规则：**

- **默认拒绝，从不默认允许。** 应用没在运行、socket 连不上、桥接程序出错、等待超时，结果都是拒绝。
- **被拒绝不等于任务失败。** 因为超时而被拒绝时，任务停在 `needsYou`，保留这个请求。你回来后点“允许并继续”，岛会带着这项许可恢复 agent 会话。
- **显示完整内容。** 批准前显示完整的命令或文件路径，过长时可以展开，不做会隐藏关键部分的截断。
- **不建立第二套长期规则。** “允许”只对这一次请求生效。想要长期放行某类命令，在 agent 自己的权限配置里设置。

**M0 的验证结果：**

- **Claude Code：已验证。** 无终端模式下 `PermissionRequest` hook 会触发，可以阻塞等待（已测 150 秒），超时和不表态都是拒绝。被拒后用 `--resume` 告知“用户已批准”，agent 会重新执行，“允许并继续”成立。不采用 `--permission-prompts host`，因为它要求宿主一直持有 agent 的管道，与进程脱离冲突。
- **Codex：hook 需要用户信任一次。** Codex 只运行信任过的 hook（按内容哈希记录）。Topside 的 hook 命令固定在应用包里，内容不变，所以理论上信任一次即可长期有效；这一点和“按次注入的 hook 能否被信任”还在验证。**Topside 不使用 `--dangerously-bypass-hook-trust`**：它会让仓库自带的未信任 hook 一起运行，对不可信仓库派活时等于执行仓库作者的任意命令。
- **Codex 的保底方案：只靠沙箱。** 用户没有信任 hook 时，Codex 以 `workspace-write` 运行，越界操作直接失败（M0 验证：不会发起审批，也不会被自动审核器放行）。任务照常完成，结果卡片里列出被沙箱阻止的操作（从 agent 的回复中识别）。这时岛上不会出现 Codex 的审批请求，设置里提示“信任 Topside 的 hook 后可在岛上审批”。

### 8.5 结果的计算

任务的所有步骤完成后，引擎自己计算结果，不依赖 agent 的自述：

- **改动**：在工作区里对比基线提交，包括已提交、未提交和未跟踪的文件。得到文件列表和增删行数。
- **验证**：最后一次 `shell` 验证步骤的退出码和输出尾部。没有验证步骤时显示“未验证”，不显示“通过”。
- **总结**：agent 最后一步的结束消息。
- **用量**：事件流里报告的耗时、轮数、费用或 token 数，有什么显示什么。

**没有任何改动也是一种结果。** 任务是提问或调研时这是正常的，卡片显示 agent 的回答而不是改动统计。

### 8.6 对外的动作

“开 PR”是唯一会把内容发到你机器之外的动作。它的步骤是：如有未提交的改动则提交 → 推送分支 → 用 `gh pr create` 创建 PR。执行前的确认对话框显示：推送到哪个远端、分支名、PR 标题和正文（可编辑）。没有安装 `gh` 或没有登录时，这个动作显示为不可用并说明原因。

### 8.7 窗口

- 无边框、不激活的 `NSPanel`，层级高于菜单栏，在所有 Space 和全屏应用上可见，不出现在 Mission Control 和窗口切换器里。
- 刘海的位置和尺寸从 `NSScreen` 的 `safeAreaInsets`、`auxiliaryTopLeftArea`、`auxiliaryTopRightArea` 计算。没有刘海时使用固定尺寸的虚拟胶囊。
- 多显示器：默认显示在主屏，可设置为跟随鼠标所在屏幕或固定某一块。监听屏幕配置变化后重新定位。
- 窗口本身保持展开态的最大尺寸并且透明，形态变化是内部 SwiftUI 视图的动画。透明区域不拦截鼠标事件。
- 派活输入框需要键盘输入，这时面板临时成为 key window。收起后焦点还给原来的应用。
- diff 窗口是一个普通窗口，不是岛的一部分。
- 应用以 `LSUIElement` 方式运行，没有 Dock 图标。另有一个菜单栏图标作为备用入口。

窗口层级和刘海几何是 CodeIsland（MIT）已经解决的问题，实现前先阅读它的做法，借鉴的部分保留署名。

## 9. 技术选型

| 方案 | 结论 | 理由 |
|------|------|------|
| **Swift + SwiftUI + AppKit** | **采用** | 能完全控制窗口层级和刘海几何；常驻应用的资源占用低；动画质量好 |
| Tauri / Electron | 不采用 | 刘海区域的窗口行为仍然要写原生代码；常驻内存占用高 |

- Swift 6，最低支持 macOS 14。
- 核心逻辑在 SwiftPM 包里，应用外壳的 Xcode 工程用 XcodeGen 从 `project.yml` 生成。
- 不引入第三方运行时依赖。git 操作通过调用 `git` 命令完成，不链接 libgit2。
- 通过命令行驱动 agent，而不是它们的 SDK。这样不需要内嵌 Node 或 Python 运行时，并且用的就是用户已经登录好的那个 CLI。

## 10. 非功能性要求

### 10.1 性能

| 指标 | 目标 |
|------|------|
| 按下快捷键到输入框可输入 | < 100ms |
| 回车到 agent 进程启动（worktree 已建好，不含准备命令） | < 2s |
| agent 事件到界面更新 | < 300ms |
| 空闲 CPU（没有任务在跑） | < 0.5% |
| 内存（10 个活动任务） | < 120MB |
| 50 个任务同时运行时，界面保持流畅，引擎自身的 CPU 占用 | < 5% |
| `topside-hook` 往返（不含等待你的时间） | < 30ms |

### 10.2 安全与隐私

- **隔离的边界。** worktree 保护的是你的 git 工作目录不被改乱。它不是沙箱：agent 执行的命令能访问你的整台机器。文档和首次启动引导里明确说明这一点。
- **权限。** 见 8.4。默认拒绝，没有全局跳过。
- **并发和费用。** 同时运行的任务数不设上限（D5）。这意味着额度和本机资源的消耗由你自己掌握，岛提供三样东西帮你掌握：收起态始终显示正在运行的任务数；“全部暂停”一键停下所有任务；Claude Code 的任务可以设置单任务费用上限。设置里另有一个可选的并发上限，默认关闭，想要限制的人可以打开。agent 因为触发服务端限流而失败时，任务进入 `failed` 并如实显示原因，可以重试。
- **数据留在本机。** 应用自己不发起网络请求。联网的只有 agent 本身，以及你点击“开 PR”时的 `git push` 和 `gh`。没有遥测，没有崩溃上报。
- **磁盘上的记录。** 任务的提示词和 agent 的事件流保存在本机（见 7.5），目录权限 `0700`。里面可能包含代码片段。任务关闭 30 天后自动删除事件流，只保留 `task.json`，期限可调，也可以设为立即删除。
- **不修改全局配置。** 不改 `~/.claude/` 和 `~/.codex/` 下的任何文件。
- **控制通道只对你开放。** 命令行和引擎之间的 Unix socket 放在数据目录（权限 0700）里，文件权限 0600。数据目录路径太长时（socket 路径上限 103 字节），改用 `/tmp/topside-<用户 ID>/` 下的短路径；这个目录必须由你拥有且权限为 0700，否则引擎拒绝启动，以防其他用户抢先放置 socket 来截获请求和提示词。

### 10.3 开源与分发

**许可证。** MIT（D6）。CodeIsland 也是 MIT，借鉴它的代码没有兼容问题。Notchi 是 GPL-3.0，不能搬它的代码。

**分发渠道，按优先级：**

1. **从源码构建。** 一条命令能构建并运行。
2. **GitHub Releases 上已签名、已公证的 `.app`。** 需要 Apple Developer Program 会员资格（每年 99 美元）。没有公证的应用在 macOS 15 上要到系统设置里手动放行。
3. **Homebrew cask。** 有了公证的发布包之后再做。

**仓库卫生。**

- 测试夹具是从真实运行里录制的事件流，进仓库前必须脱敏：提示词原文、代码片段、密钥、带用户名的路径都替换成占位内容。CI 里有扫描。
- 不提交任何来自 `~/.claude` 或 `~/.codex` 的原始文件。

## 11. 风险

| 风险 | 可能性 | 影响 | 应对 |
|------|--------|------|------|
| 无终端模式下，权限请求无法阻塞等待用户 | 中 | 高 | M0 比较三种机制。保底方案见 8.4 末尾，功能可用但多一次往返 |
| agent 事件流的格式与预期不符，或随版本变化 | 高 | 中 | M0 录制真实事件流做夹具；解析对未知内容宽容；夹具按 agent 版本分目录 |
| Codex 的 `--json` 漏报部分工具调用，岛上的活动显示不完整 | 已发生 | 中 | v1 如实显示已知的；以后可选读取 Codex 的会话文件（内部格式，需按版本适配） |
| 用户没有在 Codex 里信任 Topside 的 hook | 高 | 中 | 只靠沙箱的保底方案已验证安全；引导里说明信任的好处；岛上提示 |
| 新 worktree 冷构建慢，派活的等待时间长 | 高 | 中 | 每仓库可选的“要克隆的目录”；准备命令期间任务显示为“正在准备工作区”，不占用你的注意力 |
| worktree 里项目跑不起来（缺依赖、缺环境文件） | 高 | 高 | 每仓库的复制文件和准备命令（8.2）；首次派活时引导配置；始终提供“原地”模式 |
| 无人值守的 agent 做了破坏性的事 | 低 | 高 | 默认拒绝的权限模型；不提供全局跳过；Codex 沙箱保持开启；文档说明隔离边界 |
| 不限并发时，大量任务同时运行耗尽额度、触发限流或拖慢机器 | 中 | 中 | 岛上始终显示运行数；“全部暂停”；单任务费用上限；可选的并发上限（默认关闭）；限流导致的失败如实显示并可重试 |
| 任务很多时引擎或界面变慢 | 低 | 中 | 事件流用文件系统事件驱动读取，不轮询；列表分组和滚动；M1 用假 agent 做 50 个并发任务的压力测试 |
| 岛的窗口在全屏、多 Space、多显示器下表现不一致 | 高 | 中 | M0 做原型时逐一测试；借鉴 CodeIsland；保留菜单栏图标 |
| 派活输入框抢焦点或还焦点的行为不稳定 | 中 | 中 | M0 的窗口原型包含输入框 |
| 范围过大，迟迟做不出可用的版本 | 中 | 高 | 引擎先做成命令行可用（M1 结束就能派活）；每个里程碑都产出能用的东西 |
| Conductor 这类产品加上了岛的形态，或 CodeIsland 加上了派活 | 中 | 中 | 无法控制。保持小而专注，把“派活到验收”这条路径做到最顺 |
| 录制的夹具把私有内容带进公开仓库 | 中 | 高 | 脱敏是夹具入库的前置步骤；CI 扫描 |

## 12. 后续方向

按我认为的价值排序：

1. **多方案并行。** 同一个需求同时派给 Claude 和 Codex，各自在自己的 worktree 里做，完成后并排比较，选一个。当前架构下实现成本很低。
2. **自定义配方。** 从用户目录或仓库里的文件加载。仓库里的配方含有 shell 命令，首次使用前需要你审阅并信任。
3. **收编外部会话。** 可选地安装全局 hook，让你在终端里手动启动的会话也出现在岛上，并可以转成任务来验收。
4. **智能默认仓库。** 根据最前面的编辑器或终端窗口推断你想在哪个仓库派活。
5. **需求里带附件。** 粘贴截图、拖入文件。
6. **更多 agent。** Gemini CLI、OpenCode 等，每个只需要一个运行器和一组夹具。
7. **任务模板。** 把常用的需求存成带参数的模板。
8. **后台守护进程。** 让配方的后续步骤在应用没运行时也能推进。v1 里应用退出时，正在跑的那一步会跑完，但下一步要等应用回来。
