# Topside 开发计划

> 状态：Draft v0.4 · 2026-11-15（已按 M0 结果更新）
> 配套文档：[design.md](./design.md)
> v0.3 的变化：按“任务指挥台”方向全部重排。引擎先行，做成命令行可用之后再做界面。

## 1. 总体安排

八个里程碑，每个结束时都有一个可以实际使用的东西。顺序的原则：**先消除不确定性，再做出不带界面也能用的引擎，然后加岛，最后补全验收和配方。**

| 里程碑 | 结束时你能做什么 | 估时 | 依赖 |
|--------|------------------|------|------|
| M0 技术验证 | 拿到五个书面结论和两种 agent 的事件流夹具 | 4 天 | — |
| M1 任务引擎 | 在命令行里派任务，任务在 worktree 里后台跑，能查看状态 | 6 天 | M0 |
| M2 岛与派活 | 按快捷键派活，在岛上看任务进度 | 6 天 | M1 |
| M3 需要你的时刻 | 在岛上批准权限、回答问题，有提示和声音 | 4 天 | M2，M0 结论 2 |
| M4 结果与验收 | 看结果卡片和 diff，追加指令，开 PR，合入，丢弃，接管到终端 | 5 天 | M2 |
| M5 配方 | 使用“实现并验证”“先计划”“实现并复查”，跨 agent 接力 | 4 天 | M3，M4 |
| M6 开源准备 | 仓库可以公开 | 3 天 | M1 |
| M7 打磨与首次发布 | 设置、引导、历史，发布 v0.1.0 | 5 天 | 全部 |

合计约 37 个工作日。估时是按一个人全职、有 AI 辅助写代码来粗估的，没有历史数据支撑，M0 做完后应该重估。这比 v0.2 的 28 天多，因为这个方向除了岛还要做一个任务引擎。

三个可以停下来用的节点：

- **M1 结束（约 10 天）**：命令行版的任务引擎，已经能解决“并行派活互不干扰”。
- **M4 结束（约 25 天）**：可以日常自用的岛，派活、跟踪、验收的路径完整。
- **M7 结束**：可以推荐给别人用的 v0.1.0。

M3 和 M4 互不依赖，可以调换。M6 可以在 M1 之后的任何时候做。

## 3. 里程碑细节

### M0 技术验证（4 天）

这一阶段的代码是一次性的，放在 `Spikes/` 下。所有试验都在一个临时的测试仓库里做，不碰真实项目。

**任务**

1. 初始化仓库：`git init`、`.gitignore`、空的 `Package.swift`。仓库保持私有。
2. **试用对照产品。** 装 CodeIsland 和 Conductor 各用半天。记录：它们各自最顺和最不顺的地方；Conductor 的 worktree 准备流程怎么设计的；CodeIsland 的窗口行为。
3. **Claude Code 事件流录制。** 用 `claude -p --output-format stream-json` 跑几个任务：纯问答、改文件、执行命令、用到子 agent、中途被 `SIGINT`、超出费用上限。保存原始输出。确认 `--session-id`、`--resume`、`--settings` 的实际行为。
4. **Codex 事件流录制。** 用 `codex exec --json` 跑同样的场景。确认 `resume`、`review` 子命令、三种沙箱模式的实际行为。
5. **权限机制比较。** 这是 M0 最重要的一项。
   - Claude Code：分别试 `--settings` 注入 hook、`--permission-prompt-tool`、`--input-format stream-json` 三种方式。对每一种记录：无终端模式下是否触发；能阻塞多久；不回应、回应拒绝、回应允许时 agent 各自的表现。
   - Codex：试 `exec` 模式下 hook 是否触发、信任机制如何处理、`--approve-for-me` 是什么含义、沙箱拒绝一个操作时事件流里出现什么。
6. **进程脱离与重新接上。** 写一个小程序：启动一个把 stdout 重定向到文件的子进程并让它脱离，然后自己退出；再启动一次，根据 pid 和进程启动时间重新确认进程，从文件断点继续读。用一个真实的 agent 运行验证。
7. **窗口原型。** 一个最小的 AppKit 程序：屏幕顶部正中的黑色圆角面板，悬停放大，快捷键唤出一个可以输入的文本框，Esc 后焦点回到原应用。在外接显示器、内建刘海屏、全屏应用、切换 Space、插拔显示器这五种情况下测试。
8. **worktree 流程。** 手动走一遍：建 worktree、复制 `.env`、跑准备命令、agent 在里面工作、算 diff、删除。在一个 Node 项目和一个 Swift 项目上各试一次，记下卡住的地方。
9. 写 `scripts/scrub-fixtures.py`，把录制的事件流脱敏后放入 `Tests/Fixtures/`。

**完成标准：五个书面结论**

- **结论 1：事件流。** 两种 agent 的事件类型和字段清单。能否从中可靠地得到：会话 id、当前工具、运行结束及其成败、总结、用量。
- **结论 2：权限。** 每种 agent 采用哪种机制，能否阻塞等待，超时是多少。**如果某种 agent 做不到阻塞等待，它在 M3 里采用设计文档 8.4 末尾的保底方案，在这里定下来。**
- **结论 3：进程管理。** 脱离和重新接上的方案是否可行，是否改用 `claude --bg`。
- **结论 4：窗口。** 需要的 `NSPanel` 配置，五种情况下的表现，输入框的焦点行为。
- **结论 5：对照产品。** 试用后，设计文档 2.3 的定位是否仍然成立，有没有要调整的范围。

做完后更新 `design.md` 里标了“需要 M0 验证”的部分，并重估后续里程碑。

### M1 任务引擎（6 天）

不做界面。目标是一个只用命令行就能派活和管理任务的引擎。

**任务**

1. `TopsideCore`：`TopsideTask`、`Recipe`、`Step`、`RunEvent`、`TaskStatus`，任务状态机 `reduce(task, event) -> (task, [effect])`。
2. 状态机测试：正常流程、乱序和重复事件、进程异常退出、同目录的原地任务排队。
3. `AgentRunner` 协议，`ClaudeCodeRunner` 和 `CodexRunner`：生成命令行、解析事件流。用 `Tests/Fixtures/` 里 M0 录制的 16 个场景做解析测试。按 M0 的发现处理：一步是否完成看进程退出而不是第一个 `result`；Claude Code 的多个 `result`；中断由引擎记录；Codex 没有费用字段。
4. `ProcessSupervisor`：照 `Spikes/m0-detach/detach.py` 的做法启动脱离的进程，输出重定向到文件，持续读取文件，监听进程退出，重启后用 pid 加启动时间重新接上。
5. `WorkspaceManager`：选择满足最低版本的 git（M0 发现 PATH 里可能是 2.16）；建 worktree 和分支、复制文件、跑准备命令、用临时索引计算改动统计、删除。原地模式下的同目录互斥。照 `Spikes/m0-worktree/worktree_flow.py` 的步骤实现，它的八个检查点直接改写成测试。
6. 持久化：`task.json` 的原子写入和启动时加载。
7. `TaskEngine`：把以上串起来。这个里程碑只支持单个 `agent` 步骤的“快速”配方，访问级别固定为“工作区内”，需要批准的操作一律被拒绝（M3 再接上批准）。
8. 并发：默认不设上限，任务派出后立即开始。实现一个可选的上限（默认关闭）和“全部暂停”。事件流的读取用文件系统事件驱动，不轮询，保证任务多时引擎不变慢。
9. `topside` 命令行：`topside serve`（前台运行引擎）、`run`、`list`、`logs <任务>`、`stop <任务>`、`discard <任务>`。命令行通过本地 socket 和引擎通信，这个通道之后应用也用。
10. `scripts/fake-agent.sh`：按夹具回放事件流的假 agent，让引擎的集成测试不需要真的调用模型。
11. CI：`swift build`、`swift test`、`check-no-private-data.sh`。

**完成标准**

- `swift test` 全部通过，其中引擎的集成测试用假 agent 跑完整的任务生命周期。
- 用 `topside run` 在同一个仓库上同时派 3 个任务（Claude Code 和 Codex 都有）。每个任务在自己的 worktree 里，互不干扰，主工作目录没有任何变化。`topside list` 显示的状态和实际一致。
- 任务运行中杀掉 `topside serve` 再启动，任务没有中断，状态和日志接续正常。
- 运行中的 agent 被 `kill -9` 后，任务变为 `failed`。
- 用假 agent 同时派 50 个任务，全部立即开始、全部正常结束，期间引擎自身的 CPU 占用低于 5%。
- `TopsideCore` 和 `TopsideEngine` 的源码里搜不到 `claude` 或 `codex` 字样。

### M2 岛与派活（6 天）

**任务**

1. XcodeGen 工程，`LSUIElement` 应用，菜单栏备用图标。应用内嵌引擎，取代 `topside serve`。
2. `TopsidePanel` 和 `NotchGeometry`：按 M0 结论 4 实现，区分有刘海和无刘海，监听屏幕配置变化。
3. 收起态：运行数、等你处理数、待验收数。
4. 展开态：任务列表，按紧急度排序，每行显示状态、标题、agent、当前步骤和当前工具、时长。空状态里提示派活的快捷键。
5. 形态切换动画，悬停展开和移出收起的延时。
6. **派活输入框**：全局快捷键唤起；需求输入；仓库、agent、配方、工作区四个选项，带默认值；`@` 搜索仓库；`↩` 派出，`⌘↩` 连续派出；收起后焦点归还。
7. 仓库列表：记住用过的仓库，支持拖入文件夹添加。
8. 任务行的 `⋯` 菜单里与引擎直接对应的动作：查看活动、暂停、打开工作区、复制分支名和路径、丢弃。
9. 用假 agent 加多任务夹具做界面调试。

**完成标准**

- 在任意应用里按快捷键、输入一句话、回车，5 秒内任务出现在岛上并开始运行，原应用的焦点和输入不受影响。
- 外接显示器和内建屏上都能正确显示，插拔显示器后位置自动修正。
- 同时跑 3 个真实任务，岛上的状态变化与 `topside list` 一致。
- 用假 agent 同时跑 30 个任务，列表可以滚动和按仓库分组，展开和收起的动画不掉帧。
- 退出并重新打开应用，正在运行的任务继续显示并且状态正确。
- 没有任务运行时，CPU 占用接近 0。

### M3 需要你的时刻（4 天）

范围取决于 M0 的结论 2。

**任务**

1. `TopsideIPC` 和 `topside-hook`：权限请求的请求和应答。连不上、出错、超时一律输出拒绝。
2. 运行器在启动 agent 时注入每次运行的 hook 配置（Claude Code 用 `--settings`，Codex 用 `-c`），不修改全局配置。
2a. Codex 的 hook 信任：检测 Topside 的 hook 是否已被信任；未信任时以只靠沙箱的方式运行（M0 已验证安全），并在岛上和设置里提示如何信任。具体流程取决于 M0 中还没做完的信任测试。
3. `PermissionBroker`：接收请求，关联到任务，任务进入 `needsYou`，把你的决定传回。
4. 超时被拒后的“允许并继续”：带着这项许可恢复 agent 会话。
5. agent 提问后停下的情况：识别出运行以问题结束，任务进入 `needsYou`，在岛上输入回复后作为追加指令继续。
6. 提示态：6.4 表里的各个时刻，自动收回，多个提示排队。
7. 展开态里 `needsYou` 的任务显示内联的允许和拒绝按钮，以及回复输入框。
8. 提示音和勿扰开关。
9. 把下面的安全场景写成自动化测试（用假 agent 驱动 `topside-hook`）。

**完成标准**

- 在岛上点允许，agent 继续执行那个操作；点拒绝，agent 收到拒绝并继续工作。两种 agent 都验证。
- **下面每种情况的结果都是拒绝，没有任何一种情况下操作被自动放行：应用没在运行；应用在等待期间被强制退出；`topside-hook` 收到格式错误的应答；等待超时。这一条有自动化测试，不通过不能进入下一个里程碑。**
- 超时被拒后，任务停在 `needsYou`。点“允许并继续”后任务恢复并完成那个操作。
- 两个任务同时请求权限，两个请求分别处理，不会串。
- 检查 `~/.claude/` 和 `~/.codex/` 下的配置文件，与开始开发前的备份一致。

### M4 结果与验收（5 天）

**任务**

1. 结果计算：改动统计、总结、用量。没有改动时的处理。
2. 结果卡片视图。agent 的总结用引号和事实区分开。
3. **diff 窗口**：解析统一 diff 格式，按文件分组，只读显示，增删行着色。窗口里有“在编辑器中打开工作区”。
4. 追加指令：在同一个 agent 会话里继续，任务回到 `running`。
5. 接管到终端：在工作区里打开终端并执行恢复命令。先支持 Ghostty（你在用的终端），其他终端的保底方案是把命令复制到剪贴板并打开终端应用。
6. 开 PR：检查 `gh` 是否可用和已登录；确认对话框显示远端、分支、标题、正文；提交、推送、创建；把 PR 链接记到任务上。
7. 合入本地分支：前置检查（主工作目录干净、处于基线分支），不满足时说明原因。
8. 保留分支、丢弃（带确认）。
9. 任务关闭后进入历史。历史列表的最简版本：标题、结局、时间，可以重新打开结果卡片。
10. `failed` 状态的卡片：失败的步骤、原因、输出尾部，以及重试、追加指令、接管、丢弃。

**完成标准**

- 完整走通一次：派活 → 运行 → 结果卡片 → 看 diff → 追加一条修改意见 → 再次完成 → 开 PR。全程不打开终端。
- 结果卡片上的文件数和增删行数与在工作区里手动执行 `git diff --stat` 的结果一致，包括有未跟踪新文件的情况。
- 主工作目录有未提交改动时，“合入本地分支”不可用并显示原因。
- 丢弃之后，worktree 目录和 `topside/` 分支都不存在了，仓库的其他分支和工作目录没有变化。
- “开 PR”在点确认之前不执行任何推送。

### M5 配方（4 天）

**任务**

1. 引擎支持多步骤配方：步骤顺序推进，步骤之间传递产出。
2. `shell` 步骤和 `Verifier`：执行验证命令，保留输出尾部，按退出码判定。
3. 失败后交回 agent 重试的循环，带重试上限。
4. `gate` 步骤：计划确认。岛上显示计划摘要，可以确认、给修改意见、取消。
5. 只读访问级别：计划步骤和复查步骤使用。
6. 复查步骤：`AgentChoice.other` 的解析，复查提示词模板，复查意见附到结果上。
7. 结果卡片上的“让另一个 agent 复查”和“把意见交给原 agent 处理”。
8. 四个内置配方和它们的提示词模板，放在 `Resources/Recipes/`。
9. 每仓库配置的界面：要复制的文件、准备命令、验证命令。首次对一个仓库派活时的引导。
10. 任务行上的步骤进度显示（计划 ✓ 实现 ◐ 验证 ○）。
11. 派活输入框里的配方选择。

**完成标准**

- “实现并验证”：故意派一个会让测试失败的任务，观察到验证失败 → 输出交回 agent → agent 修复 → 验证通过，岛上的步骤进度如实反映这个过程。
- 重试用尽后任务进入 `failed`，卡片上显示最后一次验证的输出。
- “先计划”：计划步骤运行期间工作区里没有任何文件变化；不确认就不会进入实现步骤。
- “实现并复查”：用 Claude 实现、Codex 复查，以及反过来，两种组合都走通。复查步骤没有改动任何文件。
- 没有配置验证命令的仓库，结果卡片显示“未验证”，不显示“通过”。

### M6 开源准备（3 天）

**任务**

1. 定名字（Q1）：检查 GitHub、Homebrew、域名上是否冲突，全局替换代号。
2. 定许可证（Q2），加 `LICENSE`。核对借鉴代码的许可证并保留署名。
3. `README.md`：这是什么、一段演示动图、和 CodeIsland 及 Conductor 的区别、从源码构建、支持的 agent、隔离的边界和安全模型、已知限制。
4. `CONTRIBUTING.md`：构建和测试、如何录制和脱敏夹具、如何改进配方的提示词模板、PR 要求。
5. `docs/writing-a-runner.md`：以 `CodexRunner` 为例说明如何接入一个新 agent。
6. Issue 模板：bug、新 agent 接入请求、配方建议。
7. 公开前的检查：过一遍完整的 git 历史确认没有私有数据；在一台干净的机器上按 README 构建。

**完成标准**

- 一个没看过这个项目的人，只按 README 操作，能在 10 分钟内从源码构建并派出第一个任务。
- 按 `writing-a-runner.md` 给假 agent 写一个运行器，不需要改 `TopsideCore` 和 `TopsideEngine` 的任何代码。
- `check-no-private-data.sh` 对整个 git 历史通过。

### M7 打磨与首次发布（5 天）

**任务**

1. 设置窗口：显示位置、快捷键、可选的并发上限（默认不限）、默认 agent 和配方、提示和声音、worktree 存放位置、记录保留期限、开机自启。

3. 首次启动引导：检测已安装的 agent 和 `gh`；说明隔离的边界；添加第一个仓库；试派一个任务。
4. 健康检查：agent 的 CLI 找不到或版本不在已测试范围内时给出提示。
5. 历史页完善：搜索、按仓库筛选、从历史任务“再派一次”。

8. 应用图标，Release 构建脚本。
9. 发布：有 Apple Developer 会员资格就做签名和公证，在 CI 里产出发布包；没有就只发源码，README 里说明。
10. 自己连续日用一周，记录并修掉影响使用的问题。
11. 打 `v0.1.0` 标签，写发布说明。

**完成标准**

- 在一台只装了 Claude Code 的机器上，从打开应用到完成第一个任务的验收，不需要手动编辑任何配置文件。
- 只装了一种 agent 时，另一种在界面上显示为不可用，“让另一个 agent 复查”被禁用并说明原因。
- 连续运行 24 小时并完成 20 个以上任务，内存不持续增长，没有崩溃，没有残留的孤儿进程。

## 4. 测试策略

| 层 | 方式 | 何时跑 |
|----|------|--------|
| 任务状态机 | 单元测试，输入是事件序列，断言状态和副作用 | 每次提交（CI） |
| 运行器解析 | 夹具测试：每个 agent 的每个版本一个目录，原始事件流进，归一化事件出 | 每次提交（CI） |
| 引擎集成 | 用假 agent 在临时 git 仓库里跑完整的任务生命周期，包括多步骤配方 | 每次提交（CI） |
| 工作区管理 | 在临时 git 仓库上测试建、算 diff、删，断言主工作目录不变 | 每次提交（CI） |
| 权限安全 | 用假 agent 驱动 `topside-hook`，覆盖 M3 完成标准里的所有拒绝场景 | 每次提交（CI） |
| 私有数据 | 扫描个人路径和常见密钥格式 | 每次提交（CI） |
| 界面 | 用假 agent 驱动真实界面做人工检查；关键视图做 SwiftUI 预览 | 每个里程碑 |
| 端到端 | 手动检查表：真实 agent × 配方 × 显示器配置 | M2、M4、M5、M7 结束时 |

假 agent 是这个测试策略的核心：它让绝大部分测试不需要调用模型，因此快、不花钱、结果可重复。真实 agent 只在录制夹具和端到端检查时使用。

agent 升级后重新录制夹具放到新的版本目录下，测试会指出哪些字段变了。这也是社区最容易参与的贡献方式。

## 5. 开发期的安全约定

- 所有试验和端到端测试都在专门的测试仓库里做。在引擎的工作区测试通过之前，不对真实项目派活。
- 开始前备份 `~/.claude/settings.json` 和 `~/.codex/config.toml`。本项目的设计是不修改它们，备份用来验证这一点。
- “开 PR”的开发和测试使用一个专门的私有测试仓库作为远端。
- 录制的夹具进版本库之前必须经过 `scrub-fixtures.py` 并人工检查，把提示词原文、代码片段、密钥、带用户名的路径替换成占位内容。
- 仓库在 M6 的公开前检查完成之前保持私有。

## 7. M0 之后的重估（2026-11-15）

M0 的结果见 `docs/m0-findings.md`。两个核心设计（Claude Code 的权限 hook、进程脱离）都成立，没有出现需要改变方向的问题。
